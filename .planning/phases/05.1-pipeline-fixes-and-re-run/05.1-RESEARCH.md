## Blocker 1: ACCEL cuSolver Failure

### Exact Error

```
jaxlib/gpu/solver_handle_pool.cc:37: operation gpusolverDnCreate(&handle) failed: cuSolver internal error
```

Occurred in `create_train_state(rng_init)` inside `examples/maze_plr.py`, line 814, at the very start of the ACCEL run (before any training step). This is a JAX JIT compilation step that triggers GPU cuSolver handle initialization.

### Root Cause Analysis (HIGH confidence)

The error fires at the 4th sequential run in the same shell process chain. The three preceding ES runs each ran for approximately 2-3 hours inside the same sequential bash script (`scripts/run_phase5_sequential.sh`). Despite Python processes exiting normally, JAX/CUDA can leave GPU resources (handles, memory contexts) in a state that prevents a new process in the same session from initializing cuSolver cleanly.

Evidence: The error is `gpusolverDnCreate(&handle) failed`, not a "library not found" or "driver version" error. Handle creation failures are GPU resource/context issues, not missing libraries. The JAX version (0.5.3) and jaxlib version (0.5.3) are consistent between all four runs — there is no version mismatch. The ES strategy runs all used CMA-ES internally (including SVD-based covariance updates) without any cuSolver errors, meaning the GPU was functional before the ACCEL run.

### Additional Issue Discovered: Missing --use_accel Flag (HIGH confidence)

The launcher script `scripts/run_phase5_sequential.sh` runs `examples/maze_plr.py` with NO command-line flags:

```bash
$PYTHON examples/maze_plr.py \
  --run_name phase5-accel \
  --project es-accel \
  --seed $SEED \
  --num_updates $UPDATES
```

The `--use_accel` flag defaults to `False` in `maze_plr.py`. Without `--use_accel`, the script runs as PLR (Prioritized Level Replay), not ACCEL. For a valid comparison, the baseline must use `--use_accel` to enable the mutation branch that defines ACCEL. This must be fixed in the launcher alongside the cuSolver fix.

### Fix

Run ACCEL in an entirely separate, fresh bash invocation — not as a continuation of the ES sequential run. A standalone script or manual command in a new tmux window, after the ES script has exited, gives cuSolver a clean CUDA context. Add `--use_accel` flag.

```bash
# In a NEW tmux window or after ES script exits cleanly:
unset XLA_FLAGS
/cs/student/project_msc/2025/csml/gmaralla/miniconda3/envs/jax_env/bin/python examples/maze_plr.py \
  --run_name phase5-accel \
  --project es-accel \
  --seed 42 \
  --num_updates 20000 \
  --use_accel
```

## Blocker 2: SV-CMA-ES valid_fraction Collapse

### Observed Behavior (HIGH confidence — directly from metrics.csv)

- Updates 0–5398: valid_fraction on es_step ≈ 1.0 (stable, many steps at exactly 1.0)
- Update 5399: valid_fraction drops from 1.0 to **0.0** in a single step
- Updates 5399–20000: valid_fraction = 0.0 (100% of the remaining 14,601 updates)
- The collapse is permanent — no self-recovery

During the collapse, mean_regret also drops to exactly 0.0 (no valid candidates to compute regret from).

### Root Cause Analysis (HIGH confidence)

The Stein repulsion gradient is applied to particle means unconditionally, every es_step, with no bounds or decay. Over 5399 steps with `sv_epsilon=0.01`, this accumulates to a total displacement of up to `5399 * 0.01 = 53.99` units in latent space — far beyond the VAE's training distribution (which has unit normal priors, so valid latents are roughly in `[-3, 3]^64`). The repulsion direction is computed in behavior space (kernel K from behavior sigs) and applied to latent-space means; since behavior space and latent space are not aligned, the repulsion direction can point toward regions of the VAE manifold that decode to invalid mazes.

At step 5399, both particle means have drifted sufficiently far that every single one of the 16 pop_size candidates decoded from those means fails the solvability/complexity gate. The gate is strict: `flood_fill_solvable AND (min_obstacles >= 5 AND min_distance >= 3)`.

The CMA-ES baseline (one particle, no repulsion) maintains valid_fraction > 0.9 throughout because the CMA-ES covariance naturally contracts toward high-fitness regions, keeping the mean in a valid latent neighborhood. With N particles and ongoing repulsion, the means are actively pushed apart with no attractor pulling them back toward validity.

### Proposed Fix: New VAE Checkpoint

The user's collaborator has externally validated a new VAE checkpoint. If this checkpoint has a more uniform valid manifold (the decoder more reliably produces solvable, complex mazes across a wider region of latent space), the collapse would occur later or not at all. The existing loader code in `accel_training/vae_decoder.py` works with any checkpoint of the same architecture. Place the new checkpoint in `vae/` when available and update `vae_checkpoint` in `config.yml`.

### Backup Fix: Stein Repulsion Mean Clamping

If the new checkpoint alone does not prevent collapse, add an L2-norm clamp on particle means after Stein repulsion in `svcmaes_strategy.py`. This is a minimal one-line change to `new_mean_i` computation:

```python
# In SVCMAESStrategy.tell(), after: new_mean_i = new_particles[i]["es_state"].mean + repulsion[i]
new_mean_i = new_mean_i / jnp.maximum(jnp.linalg.norm(new_mean_i), clamp_radius)
# or equivalently:
new_mean_i = jnp.clip(new_mean_i, -clamp_radius, clamp_radius)
```

A clamp radius of 3.0 (matching the approximate extent of the VAE's training distribution) would prevent means from drifting into invalid latent space regions. However, this is a secondary fix — first try the new checkpoint.

### Backup Fix: SV-CMA-ES Restart on Collapse

Analogous to the CMA-ES IPOP restart: if all valid_frac == 0.0 for an es_step, re-initialize both particles from fresh random means. This prevents permanent collapse:

```python
# In train.py, after es_step for sv_cma_es:
if es_strategy_name == "sv_cma_es" and valid_frac == 0.0:
    rng, rng_restart = jax.random.split(rng)
    es_state = es_strategy.init_state(rng_restart, {**es_config, "sv_n_particles": n_sv})
    n_sv_restarts += 1
```

## Blocker 3: CMA-ES Restart Threshold

### Observed Behavior (HIGH confidence — directly from logs)

- Config: `cma_restart_threshold: 0.01`, `es_sigma_init: 0.5`
- Total restarts in 20k run: **1** (at update 52)
- The single restart message: `[update 52] CMA-ES restart #1 (sigma collapsed)`
- No second restart was logged despite the run completing 20k updates

The threshold 0.01 fires only when sigma < 0.5 * 0.01 = 0.005 (absolute value, since sigma_init is stored separately). This is extremely tight — sigma must collapse to near-zero before a restart fires.

### Target: 3-5 Restarts in 20k Updates

The user's candidate threshold of 0.05 is well-motivated:
- At sigma_init=0.5, threshold 0.05 fires when sigma falls below 0.025 (5% of initial)
- CMA-ES typically converges sigma by ~2-3 orders of magnitude over a run
- With threshold 0.05, a restart fires earlier in each convergent phase
- Expected behavior: 3-5 restart cycles each lasting ~3,000-5,000 updates

### Fix

Update `accel_training/config.yml`:

```yaml
cma_restart_threshold: 0.05   # was 0.01 — fires at sigma < 0.025 (5% of sigma_init=0.5)
```

The `es/n_restarts` metric is already logged to WandB in `train.py` (line 712: `log_dict["es/n_restarts"] = n_restarts`). Verify the sawtooth pattern in WandB's `es/std` metric after the re-run.

```python
def load_vae_params(checkpoint_path):
    """Load the full VAE parameters from a pickle checkpoint."""
    with open(checkpoint_path, "rb") as f:
        data = pickle.load(f)
    return data['params']

def extract_decoder_params(full_params):
    """Extract decoder parameters from the full VAE checkpoint."""
    key_map = {
        'LSTMCell_2': 'LSTMCell_0',
        'LSTMCell_3': 'LSTMCell_1',
        'LSTMCell_4': 'LSTMCell_2',
        'LSTMCell_5': 'LSTMCell_3',
        'Dense_0': 'Dense_0',
    }
    return {key_map[k]: v for k, v in full_params.items() if k in key_map}
```

## Common Pitfalls

### Pitfall 1: Evaluating SV-CMA-ES Checkpoints from the Collapsed Run

**What goes wrong:** The SV-CMA-ES run completed 20k updates, but from update 5399 onward, the PLR buffer received no new ES-generated levels. The buffer was frozen with ~4000 levels generated before the collapse. Checkpoints from updates 5399–20000 represent an agent trained exclusively on replay of pre-collapse levels, not ongoing ES discovery.
**Why it happens:** The solvability gate silently drops all candidates; the PLR buffer stops receiving new levels but the agent continues training on replays.
**How to avoid:** For the final comparison figures, use the SV-CMA-ES re-run (with new VAE checkpoint) rather than the collapsed run. The collapsed run's checkpoints are not representative of SV-CMA-ES's intended behavior.
**Warning signs:** `valid_fraction` = 0.0 on all es_step rows in metrics.csv after update 5399.

### Pitfall 2: ACCEL Runs as PLR Without --use_accel

**What goes wrong:** `maze_plr.py` with `--use_accel False` (default) is PLR, not ACCEL. The comparison would be "NS-ES vs PLR", not "NS-ES vs ACCEL". This invalidates the thesis comparison claim.
**Why it happens:** The launcher script passes no `--use_accel` flag. The argparse default is `False`.
**How to avoid:** Always include `--use_accel` when running the ACCEL baseline.
**Warning signs:** WandB shows `update_state: DR` updates but no `update_state: MUTATION` updates — ACCEL requires mutation updates.

### Pitfall 3: Using Old VAE Checkpoint for SV-CMA-ES Re-run

**What goes wrong:** Running SV-CMA-ES with `checkpoint_420000.pkl` again without the new checkpoint repeats the collapse at the same point.
**Why it happens:** The collapse mechanism is deterministic with the same seed and same VAE manifold.
**How to avoid:** Wait for the new VAE checkpoint before launching SV-CMA-ES re-run.
**Warning signs:** valid_fraction collapses again around updates 5000-6000 if using old checkpoint.

### Pitfall 4: Evaluating ACCEL Using maze_plr.py's Internal Checkpoint (orbax) vs the Standalone evaluate_checkpoints.py

**What goes wrong:** maze_plr.py saves checkpoints via `orbax.checkpoint.CheckpointManager` to `checkpoints/phase5-accel/42/models/`. `evaluate_checkpoints.py` loads from `runs/phase5-accel/checkpoint_XXXXXXX/agent_params.pkl`. These are incompatible formats.
**Why it happens:** The ACCEL baseline uses the DCD codebase's orbax checkpointing; the ES scripts use a custom pickle format.
**How to avoid:** Either (a) add eval capability to maze_plr.py's own orbax checkpoint loader or (b) modify the ACCEL run to additionally save a pickle-format checkpoint at `runs/phase5-accel/`. The latter is simpler.
**Warning signs:** `evaluate_checkpoints.py --all` fails to find any checkpoints in `runs/phase5-accel/`.

### Pitfall 5: cuSolver Error on Prowl Due to Previous JAX Sessions

**What goes wrong:** If any other JAX session is currently running on sideswipe/prowl, the ACCEL run may hit the same cuSolver failure even in a fresh shell.
**Why it happens:** CUDA contexts from other users or concurrent processes can consume cuSolver handles.
**How to avoid:** Check GPU occupancy with `nvidia-smi` before launching ACCEL. Run on whichever of sideswipe/prowl has a free GPU.
